EMOP/Interoperability

Interoperability

Ten FHIR R4 resources ship with EMOP: code systems for the governorates, payers, care sectors and identifier types, a value set for each, and a map from national codes to standard concepts.

EMOP is a model for storing and analysing records. Exchange standards address a different problem: moving one patient's data between systems. The two are complementary, and this page is the bridge — a loadable terminology package plus guidance for the elements where a generic mapping is not enough.

What ships#

ResourceContent
CodeSystem governorate27 governorates, ISO 3166-2 codes, Arabic and English designations, regional grouping
CodeSystem insurance scheme6 payer organisations with scheme type
CodeSystem care sectorCivil, military, police, university
CodeSystem identifier typeNational identity number, passport, military, refugee
ValueSet × 4One per code system, for binding an element
ConceptMap7 national codes to standard concepts, each carrying its official status
BundleAll of the above as one collection

All ten validate against the official FHIR R4 JSON schema. Resource names follow R4, and every resource is marked draft and experimental.

Loading

curl -X POST -H 'Content-Type: application/fhir+json' \
  --data-binary @fhir/Bundle-emop-terminology.json \
  https://your-fhir-server/fhir

Generated, not hand-written

The resources are derived from the same SQL that populates the database, so a published code cannot drift from the stored one:

python3 fhir/build_terminology.py
Status of the content

Governorates, payer organisation names, care sectors and identifier types are genuinely published and usable as they stand. The clinical and tariff codes in the concept map are illustrative: codes prefixed EX- are issued by no Egyptian authority, and each mapping says so in its own comment. No benefit schedule or tariff is included anywhere.

Identifiers#

One Patient.identifier entry per national_identifier row, so a patient holding a national identity number and a passport produces two entries rather than one overloaded field.

identifier.period.startvalid_start_dateRequired

Identity is not the primary key

A national identity number belongs in the identifier list, never in the resource id. The resource id is a server key, meaningless outside the system that issued it; a national identifier is a real-world identifier that must survive being moved between systems. Conflating them makes re-linking unreliable and leaks the identifier into every URL that references the patient.

Names#

Both name forms live on one resource. preferred_language states which to display; it does not mean the other should be dropped. When the Arabic form is the legal name, mark it as the official use and keep the Latin form as an additional entry.

Overlapping coverage is legitimate — supplementary private cover alongside a public scheme is common — so emit one coverage resource per row rather than collapsing them into one.

Organisations and encounters#

Facility sector maps to organisation type; the Ministry facility code becomes an organisation identifier; the governorate binds to the governorate code system. Referral priority maps to encounter priority.

Two Egyptian facts have no standard element: care sector on a visit, and teaching status or urban and rural catchment on a facility. The honest options are an extension or a separate observation. Overloading organisation type or inventing a field on the encounter is not one of them.

Coded values in both directions#

When exporting a diagnosis or procedure, emit two codings on the same element: the national source code, and the standard concept it maps to. The receiving system uses whichever it understands, and the mapping stays auditable rather than being resolved by a lossy guess at the boundary.

Why no conformance profiles#

An implementation guide asserts conformance rules — which elements are mandatory, which bindings are required, what makes a payload valid. Egypt has no publicly codified national FHIR guide to align those rules to. Publishing profiles now would mean guessing at national requirements and presenting the guess as a standard, which is the same overreach as inventing official code lists — the practice design principles rules out.

Terminology can be published honestly today, because the governorates, payer organisations, care sectors and identifier types are facts. Conformance rules are not yet. A later release can add profiles and structure maps once there is a national guide to conform to, or once an implementer states their constraints.
